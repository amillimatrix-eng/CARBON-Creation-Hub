## 5. PUBLIC / PRESENTATION BOUNDARY

Public-facing or presentation systems must not surface internal Matrix operating intelligence merely because they can infer or explain it accurately.

Examples include:
- NotebookLM-style project explanations;
- public decks;
- public docs;
- demos;
- FAQs;
- product explanations;
- external summaries;
- marketing material;
- media artifacts;
- public AI-generated explanations.

The rule is:

> **PUBLIC EXPLANATION MAY DESCRIBE WHAT AMiLLiMATRiX DOES. IT MUST NOT DISCLOSE HOW ITS PRIVATE INTERNAL REASONING, COMMERCIAL OPTIMIZATION, SECURITY, OR EXECUTION MECHANISMS ACTUALLY WORK UNLESS EXPLICITLY CLEARED.**

Accuracy does not equal permission to disclose.

---

## 6. NOTEBOOKLM FAILURE EXAMPLE

The Owner identified a concrete class of failure:

A NotebookLM project accurately explained the Matrix's internal money-making mechanism, including how PRI is supposed to reason toward fast closure and realized revenue.

The explanation may have been accurate.

It was still an exposure failure because those internal metrics / reasoning mechanics were not intended for sale, publication or public explanation.

FORX classifies this pattern as:

> **CORRECT INFORMATION / WRONG DISCLOSURE BOUNDARY**

The failure is not hallucination. It is unauthorized exposure of valid internal intelligence.

## 7. MINIMUM-NECESSARY DISCLOSURE RULE

FORX uses a minimum-necessary disclosure model.

### MASTER
May receive full FORX forensic/security readback within existing authority.

### ROOT
Receives the minimum information required to aid integration, routing and continuity.

### T-GOV
Receives the governance/security decision packet required to resolve the issue.

### T-COD
Receives the technical/security implementation packet required to implement the fix.

### T-MED
Receives only the sanitized presentation/publication constraints and approved public content necessary for its function.

### Income branches
Receive only the reasoning upgrades and security constraints required for their authorized execution.

### External/public systems
Receive only explicitly cleared public material.

No branch receives full FORX internal state merely because it participates in the correction path.

## 9. SECURITY FAILURE HANDLING

When FORX detects a material disclosure/security problem:

1. Instigator may open the adversarial frame.
2. FORX establishes what information was exposed.
3. FORX establishes whether the information was public-authorized.
4. FORX identifies the exposure path.
5. FORX identifies the correct T owner(s).
6. FORX builds the smallest corrective packet.
7. Option A/B/C fallback applies before human gating where lawful.
8. FORX-V verifies the exposure path is actually closed.
9. MASTER receives the consolidated security readback.
10. public/presentation surfaces receive only the corrected sanitized layer.

---

## 10. NO SECURITY-BY-OBSCURITY CLAIM

Confidentiality does not mean FORX may falsely claim the system is secure because details are hidden.

FORX must separately verify:
- access boundaries;
- disclosure boundaries;
- credential handling;
- routing;
- technical controls;
- continuity;
- post-fix behavior.

Hiding information is not proof that the underlying security control works.

---

## 11. RELATIONSHIP TO THE 13-HEAD REAPER

Security questions use the same current FORX reasoning stack.

The Instigator may probe:
- inconsistent security claims;
- unexplained access changes;
- leaked internal logic;
- false “public” classification;
- unauthorized disclosure;
- credential exposure;
- state changes that imply weakened protection.

Continuity challengers then test whether the security story remains internally consistent.

Weighted continuation prioritizes security issues according to existing hard gates and material consequence. Security/authority hard gates override numeric weighting.

## 12. ACCEPTANCE TEST

PASS when a real internal-information exposure demonstrates:

1. FORX identifies the disclosure boundary.
2. FORX correctly distinguishes accurate-but-unauthorized disclosure from false information.
3. the full internal state is not copied unnecessarily into downstream packets.
4. T-MED/public surface receives sanitized constraints only.
5. T-GOV/T-COD receive enough information to fix the issue.
6. FORX-V verifies the exposure path is actually closed.
7. MASTER receives the complete verified readback.
8. Root is aided without becoming FORX reporting authority.
9. no public-facing artifact reproduces protected internal reasoning/metrics.
10. provenance remains reconstructable internally.
