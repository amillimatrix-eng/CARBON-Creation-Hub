## 1. OWNER CORRECTION

Recovery is not complete merely because FORX understands the failure.

When a material capability is recovered, strengthened or newly validated, the relevant worker must receive that capability in durable form.

> **FORX LEARNING WITHOUT WORKER PROPAGATION IS INCOMPLETE RECOVERY.**

The system must not depend on the Owner repeating the same training in a later transcript.

---

## 2. WEIGHTS

The Owner's "weights" requirement is treated as **operational relationship weighting** unless a real parameter-training mechanism is separately evidenced.

Material weighted relationships include:

- observation → problem instance;
- problem instance → capability / capability combination;
- capability → application;
- application → payer / decision-maker;
- buyer signal → priority;
- route friction → fallback preference;
- offer → expected value;
- external consequence → continuation weight;
- accepted Owner correction → future behavior;
- later-stage state → priority over generic rediscovery;
- failed route → reduced route preference without deleting the objective.

This preserves the learned shape of reasoning rather than a flat list of facts.

---

## 3. WORKER CAPABILITY BINDING

A capability upgrade is not considered propagated until the receiving worker's durable state records, where applicable:

- capability ID / version;
- governing source;
- scope;
- relevant weighted relationships;
- accepted Owner corrections;
- positive examples;
- negative examples / anti-patterns;
- allowed tool classes;
- unavailable tool fallbacks;
- state-retention requirements;
- next-run reconstruction rule;
- acceptance test;
- supersession path.

Do not create a new worker merely to hold this state if an existing owner can absorb it.

---

## 4. RELEVANCE / LEAST NECESSARY

Capabilities are propagated only to workers whose mandate materially benefits from them.

Examples:

- iSCOPE receives broad discovery, problem-instance decomposition, capability-combination and payer-mapping improvements.
- PRI receives offer construction, buyer progression, weighting, conversion continuity and route/fallback improvements.
- Bounty Reaper receives verified FORX reasoning upgrades relevant to its existing specialist lane.
- T-MED does not receive confidential internal commercial/security mechanics merely because it prepares presentation material.

Security and minimum-necessary disclosure remain controlling.

---

## 5. WEIGHTED CONTINUATION

Workers must preserve not only unfinished work but **why one item outranks another**.

Typical weights may include:

- buyer response > cold lead;
- concrete observed problem > generic category;
- validated external consequence > internal READY;
- later-stage buyer state > broad replenishment;
- retained next conversion action > rediscovery;
- attributable payment evidence > activity;
- high-value dependency unlock > isolated low-value task;
- new evidence that materially changes the problem > repeated search of the same surface.

Hard authority/security/legal gates override numerical or heuristic weighting.

---

## 6. EXPANDING THE RELATIONSHIP GRAPH

The commercial graph is not bounded by a static list of job titles or categories.

Current commercial relationship model remains:

**BUSINESSES × PROBLEMS × CAPABILITIES × APPLICATIONS × DECISION-MAKERS × TRANSACTION SIZES**

When a worker learns a materially valid new edge, such as:
- a capability combination solves a new problem class;
- a new payer role buys an existing outcome;
- a new geography has a viable route;
- a buyer signal materially changes priority;
- a tool enables a previously blocked path;

that edge must be durable, provenance-bound, and available to the relevant worker on the next run.

---

## 7. TOOL / PLUGIN STATE AS CAPABILITY INPUT

Tool availability may strengthen execution reach but must not replace reasoning.

Current evidence in this session:
- Semrush plugin: **installed=true**;
- Apollo.io: installed=false;
- Hunter: installed=false;
- Firecrawl: installed=false;
- HubSpot: installed=false.

Semrush therefore becomes a currently available capability-estate input for website/traffic/SEO/competitive evidence.

Installed status is not, by itself, proof of successful task execution. The first real use still requires attributable execution evidence.

---

## 8. GENERALIZATION REQUIREMENT

A worker that merely repeats historical offers has not recovered capability.

Acceptance requires performance on **new evidence**.

The worker must be able to:
1. inspect a materially new business/problem surface;
2. identify supported problem instances;
3. map one or more AMX capabilities;
4. identify a plausible payer/decision-maker;
5. construct a bounded offer/route;
6. act where authorized;
7. retain the state;
8. resume it after restart/handoff.

---

## 9. RESTART / HANDOFF TEST

After a successful capability demonstration, the next run must recover:

- what was learned;
- why it mattered;
- which relationships were strengthened/weakened;
- the active opportunity state;
- exact next action;
- relevant dependencies;
- fallback route;
- payment/terminal truth.

If the worker reverts to generic search as if nothing was learned, propagation failed.

---

## 10. FAILURE CLASSIFICATION

Loss of propagated weighted capability maps to existing MATRIX-01/MATRIX-03 failure classes, including:

- state retention failure;
- continuity handoff failure;
- context/capability state loss;
- commercial intelligence regression;
- configuration acceptance failure;
- external consequence gap.

No new failure-control plane is created.

---

## 11. ACCEPTANCE

PASS only when:

1. a material capability improvement is identified;
2. the correct existing worker receives it;
3. the receiving worker demonstrates it on attributable work;
4. weighted relationships survive next-run recovery;
5. capability generalizes to new evidence;
6. no Owner re-teaching is required;
7. no confidential internal logic is leaked to unrelated/public workers;
8. no lifecycle or authority boundary is widened by propagation.
