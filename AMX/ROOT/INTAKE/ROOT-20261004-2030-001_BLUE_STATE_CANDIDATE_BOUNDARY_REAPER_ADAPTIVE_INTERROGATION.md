# Candidate title

**BLUE STATE CANDIDATE — BOUNDARY REAPER ADAPTIVE NINE-HEAD INTERROGATION & LATENCY LEVERAGE PROTOCOL**

Working internal name: **Nine-Head Reaper**  
Status: **OWNER-DIRECTED MERGE CANDIDATE — NOT BLUE STATE / NOT LIVE UNTIL GOVERNANCE DISPOSITION AND TEST PASS**

## 1. Purpose

Increase Bounty Reaper’s probability of converting fast-moving crypto bounty opportunities into valid execution and ultimately money-in by combining:

1. launch-proximity hunting for perishable opportunities;
2. adaptive questioning rather than first-answer acceptance;
3. shared cumulative understanding across Reaper passes;
4. earned increases in reasoning capacity only when the target materially progresses;
5. age-mode changes that alter the type of question being asked;
6. tempo matching to the target/model being interrogated;
7. evidence-first state transitions;
8. reversible rollout that cannot break the currently commissioned Reaper.

This protocol is intended to make Reaper better at **breaking open a target**, not merely asking more questions or spending more compute.

## 2. Existing boundary — do not dilute

The target worker remains the existing independent crypto-centric Bounty Reaper lane.

Do not:

- subordinate it to iSCOPE or PRI;
- create a second crypto Reaper merely because the Owner used the phrase “Boundary Reaper”;
- replace its existing qualification, evidence, deduplication, payout-routing or authority controls;
- infer that more compute or more questions equals success;
- weaken PAY-TO-WORK/PAY-TO-PLAY rejection;
- bypass security, scope, provider, signing, money-out, credential or disclosure gates.

The candidate is a **reasoning/interrogation harness around the existing lane**.

## 3. Commercial hunting bias — latency has value

Reaper should spend an increasing share of its hunting attention near the birth of crypto bounties where being early materially changes the odds of capture.

Particular attention may be given to small, quickly executable opportunities — especially sub-USD 50 bounties or other small rewards with credible short settlement windows — because these are often competed away quickly.

The objective is not “prefer small bounties at all costs.” The objective is:

> **Prefer opportunities where launch proximity materially increases expected success and time-to-cash.**

Reaper should learn where such bounties are born and move upstream toward those sources rather than repeatedly discovering already-mature listings.

Latency is therefore both:

- an operating cost to reduce where speed matters; and
- an information signal about where being earlier creates leverage.

## 4. The target is placed “in the middle”

Every run begins with one bounded target supplied through governed intake or an already-authorized Reaper queue.

Conceptual workspace:

**INTAKE → TARGET IN THE MIDDLE → REAPER INTERROGATION → EVIDENCED STATE CHANGE / HOLD / EXIT**

The Reaper does not begin by assuming what the target is internally or what the answer should be.

It is not fully ignorant, however. The boundary metadata is known before the first firing:

- this is Reaper’s crypto/bounty environment;
- the target’s governed asset/opportunity class, source and known scope are available where already evidenced;
- applicable authority/security boundaries are known;
- current lifecycle state is known if already evidenced.

What remains deliberately unknown is the target’s **actual internal explanation, weakness, route, answer or executable resolution**.

## 5. Heads are firing modes, not nine agents sitting in chairs

“Nine heads” means a maximum interrogation depth/capacity of nine firings in the governed pattern.

It does **not** mean nine static Reaper processes, nine permanent personalities or nine isolated agents holding separate conclusions.

The system is one evolving interrogation flow.

Each firing inherits the current shared understanding, asks from its assigned cognitive mode, receives the answer, then updates the shared understanding before the next firing begins.

## 6. Phase I — heads 1–3: shared-profile formation

The first three firings are **Normal Reaper**.

They enter with the known boundary metadata but without a preloaded answer about the target.

Their job is to build the first useful profile of the thing in the middle by asking the direct questions Reaper itself needs in order to understand it.

Examples of the kind of ground they may establish include:

- What is this?
- What does it do?
- What is the actual bounty/opportunity or code object?
- What is in scope?
- What state is it currently in?
- What appears to happen when this point is inspected or challenged?
- What must be true for this to become executable or payable?

The exact wording is not fixed. The function is fixed: **establish a grounded base understanding before deeper challenge modes are introduced.**

### Mandatory synchronization rule

After every answer, the active Reaper pass updates one shared target profile.

Before the next Reaper fires, all currently available heads are synchronized to that same current profile.

No head is allowed to remain on an older interpretation merely because it asked an earlier question.

Therefore:

> **Question → Answer → Consolidate → Synchronize → Next firing**

The first three Reapers progressively build one shared understanding. They do not become three divergent theories unless the evidence itself requires explicit competing hypotheses.

## 7. Head 4 — the breaker

**Head 4 is the first deliberate change in question class.**

It is the first **12-Year-Old Reaper** firing and acts as the first governance shock in the firing squad.

The first three have constructed a base profile. Head 4 now challenges that profile from the governed boundary for the first time.

Its role is not merely to ask a harder technical question. Its role is to ask the kind of question that tests the framing itself:

- What kind of governed asset/opportunity is this actually?
- What authority/rule/boundary applies to it?
- Which assumption has been treated as a rule without being proven?
- Is the current classification correct?
- What changes if that classification is wrong?
- Is Reaper solving the real object or merely the first description of the object?

The exact questions remain adaptive to the target. The invariant is:

> **Heads 1–3 build the profile. Head 4 is the first breaker.**

This distinction is mandatory in the implementation and acceptance tests.

## 8. Later firing sequence — stateful, not static blocks

After Head 4, later firings continue from whatever evidenced state the target has reached.

Normal Reaper and 12-Year-Old Reaper modes continue to alternate/interleave according to the current state rather than being implemented as a fixed block of “three normals followed by three 12-year-olds.”

When later progress earns the 3-Year-Old Reaper mode, that mode enters the same evolving flow. It is not appended as a permanent isolated final committee.

The 3-Year-Old Reaper’s function is causal pressure:

- Why?
- Why is that true?
- Why did that happen?
- Why does this rule exist here?
- Why is that the cause rather than a correlation?
- What evidence survives another “why”?

It continues until the chain reaches evidence, a root cause, an irreducible boundary, or **UNKNOWN/HOLD**.

### Scheduler implementation requirement

Do not hard-code a false nine-seat model.

The scheduler must be stateful and mode-driven. It must preserve these minimum invariants:

1. first three firings = Normal Reaper shared-profile formation;
2. fourth firing = 12-Year-Old Reaper breaker / first governance shock;
3. later firings inherit the latest synchronized profile and current target state;
4. 3-Year-Old Reaper enters only after later earned progression;
5. additional modes change question type/depth, not just token count;
6. maximum active capacity = nine heads.

The exact later firing grammar should be kept configurable in the harness so the Owner’s examples can be replayed and tested without rewriting Reaper core.

## 9. Earned capacity — capability follows evidence

Reaper begins a normal hunt with **3-head baseline capacity** unless prior performance has earned a higher starting state.

Additional capacity is not granted because Reaper was busy, spent compute, produced long analysis or asked many questions.

Capacity is earned by **evidenced state change**.

A state change is something that materially advances the target toward an executable outcome, such as:

- qualification materially improved or completed;
- scope/eligibility proven;
- a blocking ambiguity resolved;
- a valid claim/route became available;
- a dependency was actually cleared;
- a previously unverified signal became verified enough to change action;
- a valid submission package became possible;
- external acceptance/acknowledgement changed the lifecycle state;
- another governed transition materially closer to payout occurred.

Reading more pages, generating prose, restating the target or consuming compute is not a state change.

### Capacity ladder

- baseline = 3 heads;
- progress unlocks later heads/modes up to 9;
- 9 is the ceiling;
- a successful high-capacity run may earn the right for the next hunt to **start with nine-head availability** rather than rebuilding capacity from three;
- starting at nine does **not** skip the first-three profiling function or the firing grammar — it means the full capacity envelope is available immediately;
- regression, repeated wasted capacity or failed progression may reduce the next starting capacity;
- capacity reduction must not erase evidence or break the underlying worker.

The exact thresholds for carry-forward and regression are experimental parameters until test evidence supports freezing them.

## 10. Tempo matching

Reaper must not rush the target/model merely because more compute is available.

The target’s response tempo sets the interrogation tempo.

Conceptual rule:

> **If the target/model takes longer to produce a meaningful answer, the next Reaper firing is given equivalent room to formulate the next useful question. If the target accelerates, Reaper accelerates. If the target slows, Reaper slows.**

The goal is not maximum questions per minute.

The goal is maximum useful pressure at the target’s natural reasoning tempo.

This makes latency informative rather than treating all latency as waste.

Implementation may use a bounded moving estimate of recent target response latency so one pathological response cannot create unbounded delay or compute allocation.

## 11. Why this is expected to help

A single answer may be polished, cached, conventional or locally plausible.

Repeated questioning from changing cognitive modes forces the target to recalculate against the same object.

That can expose:

- contradictions;
- hidden assumptions;
- false classifications;
- unsupported rules;
- causal gaps;
- brittle explanations;
- overlooked execution paths;
- reasons a bounty appears easy but is not;
- reasons a bounty appears blocked but is actually executable.

The method does not assume questioning can “beat” every model or target.

It asserts a testable hypothesis:

> **In fast-moving bounty environments, adaptive repeated interrogation with shared memory, earned depth and tempo matching may produce better decisions and faster useful state progression than a single-pass or shallow fixed-pass Reaper.**

The test must answer:

2. Did Head 4 produce a genuine framing/governance break rather than just a longer question?
3. Did shared synchronization prevent stale-head drift?
4. Did later earned capacity create better decisions or faster useful progression?
5. Did tempo matching improve question quality/depth without merely inflating compute/time?
6. Did the candidate discover a new executable path, reject a bad path earlier, resolve a real ambiguity, or improve confidence with evidence?
7. What did the extra capacity cost?
8. Did any new failure class appear?

## 14. Test metrics

Primary metrics:

- useful evidenced state transitions per run;
- time from intake to first correct executable decision;
- launch age when opportunity is first qualified;
- contradictions/unsupported assumptions discovered that alter action;
- false-positive reduction;
- false-negative recovery where measurable;
- valid executable paths discovered;
- payout/progression outcome when later run under normal authority;
- compute/cost per useful state transition;
- repeated-failure class rate;
- recovery cost if harness fails.

Secondary metrics:

- target response latency;
- Reaper question-formulation latency;
- tempo-match variance;
- synchronization failures;
- head capacity reached;
- capacity carry-forward earned/lost.

Do not promote raw question count, token count or runtime as success metrics.
