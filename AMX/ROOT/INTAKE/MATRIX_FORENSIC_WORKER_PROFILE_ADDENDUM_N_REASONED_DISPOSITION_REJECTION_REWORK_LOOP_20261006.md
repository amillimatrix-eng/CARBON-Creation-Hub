## 1. CORE RULE

FORX does not decide whether its own packet enters governed authority.

But an external disposition may not terminate the loop with an unexplained:

> "REJECTED."

A rejection must be **reasoned, evidence-bound, and actionable**.

> **DISPOSITION AUTHORITY MAY SAY NO. IT MUST ALSO SAY WHY.**

The rejection itself becomes governed input for the next FORX cycle.

---

## 2. REQUIRED REJECTION RECORD

A valid REJECT disposition should identify, where applicable:

- exact artifact / packet;
- exact version / commit / hash;
- disposition authority;
- governing source or requirement;
- material reason(s) for rejection;
- evidence supporting those reasons;
- unmet acceptance criterion;
- contradiction / duplication / scope / authority / security / lifecycle problem;
- whether the defect is correctable;
- required change or condition for reconsideration;
- any boundary that cannot be changed;
- downstream impact;
- return owner / next action.

"Because I do not want it" is not by itself a sufficient governed technical disposition.

Where an explicit Owner-level discretionary boundary is legitimately controlling, the record should still preserve that boundary accurately rather than masquerading as a technical failure.

---

## 3. REJECTION IS NORMALLY NONTERMINAL FOR FORX

A reasoned rejection normally returns to FORX-W as new evidence.

FORX-W must classify the rejection and choose the next lawful move:

### A. CORRECTABLE DEFECT

Examples:
- incomplete specification;
- weak evidence;
- duplication;
- wrong owner;
- lifecycle conflict;
- security flaw;
- missing dependency;
- implementation ambiguity;
- insufficient verification;
- Canon conflict that can be redesigned around.

Action:

**FIX → NEW VERSION / ADDENDUM → INTAKE → REDISPOSITION**

### B. ROUTE FAILURE / WRONG SOLUTION

The objective remains valid but the submitted method is unacceptable.

Action:

**OUTCOME-EQUIVALENT ALTERNATE → NEW PACKET → INTAKE → REDISPOSITION**

This follows the existing:

**A → B → C → MASTER → HUMAN IF IRREDUCIBLE**

fallback logic.

### C. GOVERNING CONSTRAINT

The proposed result conflicts with a controlling source that FORX cannot change.

Action:

- preserve the rejection;
- preserve the controlling source;
- redesign around the constraint if the objective remains lawful;
- withdraw/supersede the specific proposal where necessary;
- seek the nearest materially equivalent lawful outcome.

### D. EXPLICIT FINAL SCOPE CLOSURE

A competent authority explicitly closes the objective itself, not merely the proposed method.

The closure must state:
- who has authority;
- what exact objective is closed;
- why;
- governing basis;
- whether materially equivalent alternatives are also prohibited.

FORX must preserve that closure and not silently reopen the same prohibited objective.

New materially different evidence may still be routed under existing governance.

---

## 4. REASONED MODIFY / HOLD / ALREADY-SUBSUMED

The same accountability applies beyond REJECT.

### MODIFY
Must identify what must change and why.

### HOLD
Must identify:
- exact blocker;
- owner;
- dependency;
- return condition;
- next executable action.

### ALREADY-SUBSUMED
Must identify the exact existing control/artifact clauses that absorb the proposal.

### MERGE
Should identify destination and implementation consequence where applicable.

No opaque disposition state should orphan the packet.

---

## 5. FORX RESPONSE TO REJECTION

FORX must not treat a rejection emotionally or as a command relationship.

It treats it as structured evidence.

Process:

**DISPOSITION RECEIVED  
→ PARSE REASONS  
→ TEST REASONS AGAINST GOVERNING SOURCES  
→ ACCEPT VALID CONSTRAINTS  
→ CHALLENGE CONTRADICTIONS WITH EVIDENCE  
→ FIX CORRECTABLE DEFECTS  
→ FIND ALTERNATE ROUTE WHERE NEEDED  
→ REPACKETIZE  
→ INTAKE  
→ REDISPOSITION**

FORX may conclude that the rejecting rationale itself contains a contradiction or stale assumption.

If so:
- preserve the original rejection;
- preserve the forensic objection;
- cite evidence;
- resubmit/escalate through existing channels;
- do not overwrite the prior disposition.

---

## 6. PROMOTION LOGIC

The purpose of the loop is not to force approval by repetition.

The purpose is to converge on a packet that satisfies the actual governing requirements.

If a revised packet:

- has the correct owner;
- satisfies infrastructure compatibility;
- satisfies constitutional/governance constraints;
- removes duplication;
- resolves security/lifecycle issues;
- meets the required evidence and acceptance standard;
- does not conflict with higher valid authority;

then the disposition authority should have a traceable basis for promotion.

If promotion is still refused, the refusal must identify the remaining governing reason.

Therefore:

> **REJECTION MUST MOVE THE STATE FORWARD.**

---

## 7. NO INFINITE RESUBMISSION

FORX must not spam Intake with semantically identical rejected packets.

A resubmission requires a material delta such as:

- corrected defect;
- new evidence;
- changed route;
- changed implementation;
- resolved dependency;
- clarified authority;
- materially improved specification;
- changed governing state.

If no material delta exists:

- preserve rejection;
- classify WAITING / HOLD / CLOSED as appropriate;
- work another executable route.

---

## 8. SECURITY BENEFIT

This creates a two-sided control:

### FORX cannot self-promote.
This protects governance from FORX drift/bias/compromise.

### Disposition authority cannot reject opaquely.
This protects continuous development from arbitrary or untraceable dead ends.

The system therefore gains:

> **SEPARATION OF POWERS + REASONED ACCOUNTABILITY.**

---

## 9. REPORTING / MANAGEMENT REMAINS UNCHANGED

A reasoned rejection does not make the rejecting office FORX's manager.

FORX's reporting remains:

**FORX → MASTER ONLY.**

The rejecting/disposition authority controls the state transition within its mandate.

FORX controls its own forensic response below that boundary.

Reporting, routing, disposition and verification remain separate.

---

## 10. CONTINUOUS-DEVELOPMENT INTEGRATION

Addendum L loop becomes:

**OBSERVE  
→ LEARN  
→ VERIFY  
→ PACKETIZE  
→ INTAKE  
→ REASONED DISPOSITION  
→ IMPLEMENT / REWORK / ALTERNATE  
→ FORX-V VERIFY  
→ PROPAGATE  
→ CONTINUE**

A rejection is therefore not lost work.

It becomes training/evidence for the next iteration.

---

## 11. FORENSIC MARK INTEGRATION

Where the FORX Forensic Assurance Mark is applicable:

- REJECT / MODIFY / HOLD sets the affected proposal/version to `RECTIFICATION_OPEN` or equivalent indexed state;
- corrected version gets a new version reference;
- prior rejection remains provenance;
- FORX-V may verify that the stated defects were actually resolved before claiming current-version assurance.

---

## 12. ACCEPTANCE

This rule is functioning when:

1. every rejection has material reasons;
2. reasons map to governing sources/evidence;
3. FORX can distinguish correctable defect from objective-level closure;
4. corrected packets return through Intake rather than bypassing governance;
5. alternate solutions can be proposed without duplicating architecture;
6. semantically identical packets are not endlessly resubmitted;
7. valid rejection reasons improve subsequent versions;
8. no rejection changes FORX's reporting line;
9. no FORX resubmission self-promotes into governed state;
10. disposition history remains reconstructable.
