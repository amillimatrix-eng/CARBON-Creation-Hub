## 1. OWNER DIRECTIVE

The preferred long-term outcome is not permanent dependence on external plugins/providers.

When a connected tool proves a capability materially useful, FORX should autonomously ask:

> **CAN AMX INTERNALIZE THIS CAPABILITY, OR A MATERIAL OUTCOME-EQUIVALENT VERSION OF IT, USING EXISTING INFRASTRUCTURE?**

External tools should function as:
- usable capability;
- benchmark;
- specification source;
- fallback;
- data/network provider where their unique estate is genuinely valuable.

---

## 2. CAPABILITY SOVEREIGNTY PRINCIPLE

Goal:

> **INTERNALIZE REPEATABLE REASONING, ORCHESTRATION, STATE AND WORKFLOW; RENT UNIQUE DATA OR NETWORK EFFECTS ONLY WHERE THEY ARE ACTUALLY UNIQUE.**

Do not internalize for vanity.

Internalize when it materially improves:
- resilience;
- continuity;
- cost;
- latency;
- privacy;
- autonomy;
- restart durability;
- composability;
- worker capability-awareness;
- provider independence.

## 4. INTERNALIZABILITY CLASSES

### CLASS I — HIGHLY INTERNALIZABLE
Logic/state/orchestration that AMX can reasonably own.

Examples:
- CRM state model;
- opportunity ledger;
- follow-up/task state;
- dedupe;
- weighted continuation;
- search orchestration;
- evidence extraction workflow;
- crawl scheduling;
- website/problem inspection;
- company/contact relationship graph;
- capability-to-offer mapping;
- buyer-state tracking;
- fallback routing.

### CLASS II — PARTIALLY INTERNALIZABLE
AMX can own orchestration and reasoning but may still require external data/API sources.

Examples:
- contact enrichment;
- company firmographics;
- email verification;
- intent signals;
- SEO/backlink data;
- proprietary market datasets.

### CLASS III — EXTERNALLY UNIQUE / RENT
Provider's value depends materially on:
- proprietary dataset;
- private network;
- licensed data;
- specialized infrastructure;
- legally restricted data access;
- provider-exclusive signal.

Keep provider integration unless a lawful equivalent source exists.

### CLASS IV — DO NOT REPLICATE
Do not copy or reverse-engineer:
- proprietary code;
- private algorithms;
- restricted datasets;
- protected credentials;
- vendor confidential methods;
- access controls;
- gated data outside authorization.

Outcome-equivalent implementation must be independently designed.

## 6. BUILD-VS-RENT TEST

Before building an internal equivalent, FORX should score:

- recurrence frequency;
- strategic importance;
- dependency risk;
- vendor gate frequency;
- operating cost;
- latency;
- privacy sensitivity;
- data uniqueness;
- implementation complexity;
- maintenance burden;
- expected reuse across workers;
- fallback value.

Build is preferred when:
- capability is repeatedly used;
- external friction is material;
- primitives are generic;
- AMX already owns most required infrastructure;
- internal version can reach materially equivalent outcome.

Rent is preferred when:
- provider owns unique/legal dataset;
- build cost exceeds value;
- capability is rarely used;
- maintenance/security burden is disproportionate.

---

## 7. NO DUPLICATE SYSTEM RULE

Internalization must extend existing owners.

Examples:
- CRM-like persistence should extend the current opportunity/continuation ledger rather than create a second CRM truth source.
- web discovery should extend existing discovery capability rather than create a new discovery office.
- contact enrichment should attach to existing entities/provenance rather than create a separate contact universe.

New terminology does not justify new architecture.

## 9. ACCEPTANCE FOR AN INTERNALIZED CAPABILITY

PASS only when the internal implementation can demonstrate, on real attributable work:

1. materially equivalent target outcome;
2. correct provenance;
3. no fabricated data;
4. no hidden dependency on the supposedly replaced provider unless declared;
5. restart/handoff continuity;
6. worker can discover/use the capability without Owner re-teaching;
7. security/privacy boundaries preserved;
8. cost/latency/reliability is acceptable;
9. fallback remains available if internal capability fails;
10. external provider can be downgraded from required dependency to optional/benchmark/fallback where justified.
