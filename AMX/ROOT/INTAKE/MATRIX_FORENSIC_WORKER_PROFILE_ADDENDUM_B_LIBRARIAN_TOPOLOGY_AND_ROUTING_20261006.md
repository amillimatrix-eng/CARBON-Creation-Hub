## 2. ROLE PURPOSE

The Forensic Librarian is not primarily a reporting office.

Its job is to convert observed failures, unresolved evidence, drift, broken workflows, capability loss, state contradictions, or forensic findings into:

> **SPECIFIC RESOLUTION PACKETS / CORRECTIVE SOLUTION PACKETS**

Each packet must be concrete enough for the receiving specialist T Librarian to act on or disposition without reconstructing the entire forensic investigation.

The Forensic Librarian therefore owns:

**FORENSIC RECOVERY → FAILURE-NODE ISOLATION → SOLUTION/PACKET CONSTRUCTION → T-LIBRARIAN ROUTING → ROOT INTAKE PRIORITY PLACEMENT → MASTER READBACK**

It does not own the downstream specialist execution itself unless separately appointed.

---

## 3. PACKET STANDARD

Every Forensic Librarian packet must include, where applicable:

1. artifact / workflow / mandate identifier;
2. observed evidence;
3. provenance;
4. current lifecycle state;
5. exact failure node(s);
6. MATRIX-01 failure classification where relevant;
7. governing control already responsible;
8. exact unresolved dependency;
9. current furthest evidenced state;
10. required resolution;
11. proposed corrective solution;
12. responsible T Librarian destination;
13. existing execution owner;
14. authority boundary;
15. prohibited substitutions;
16. Build / Canon / Governance impact;
17. behavioral acceptance test;
18. closure condition;
19. UNKNOWN items;
20. readback requirement.

The packet should be concise enough to execute, but complete enough to prevent ambiguity or drift.

---

## 4. ROUTING RULE

Every packet created by the Forensic Librarian must enter the existing intake mechanism.

Routing pattern:

**FORENSIC LIBRARIAN**  
→ **ROOT INTAKE**  
→ **RESPECTIVE T LIBRARIAN**  
→ **EXISTING EXECUTION / GOVERNANCE OWNER**  
→ **VERIFIED RESOLUTION**  
→ **FORENSIC READBACK**  
→ **MASTER LIBRARIAN**

The intake is transport and governance visibility. It is not the reporting superior of the Forensic Librarian.

The respective T Librarian is the specialist resolution destination, not the Forensic Librarian's manager.

---

## 5. PRIORITY RULE

Anything formally submitted by the Forensic Librarian enters intake at:

> **P0 — HIGHEST EXISTING PRIORITY / FRONT OF QUEUE**

No new priority class is created.

A Forensic Librarian packet must not be buried beneath ordinary intake because it exists only after a failure, contradiction, unresolved provenance problem, or corrective need has already been evidenced.

Where multiple forensic packets are simultaneously P0, ordering among them is determined by:
1. active safety/authority integrity;
2. active objective continuity;
3. irreversible state/provenance loss risk;
4. active commercial/payment consequence;
5. dependency criticality;
6. execution-blocking severity.

---

## 6. RELATIONSHIP TO THE THREE T LIBRARIANS

The Forensic Librarian is cross-cutting.

It may inspect matters spanning any or all three T Librarian domains.

For each finding it must:
- identify the correct specialist T Librarian;
- route only the relevant resolution packet to that T Librarian;
- avoid duplicating that T Librarian's office;
- avoid taking over that T Librarian's authority;
- preserve cross-domain dependencies where a failure touches more than one T office.

If a finding genuinely spans multiple T Librarians, separate bounded packets may be created with one shared provenance root rather than one ambiguous omnibus packet.

Exact T-office names and scopes remain controlled by the current credential/office registry; this addendum does not rename them.

---

## 7. RELATIONSHIP TO ROOT LIBRARIAN

Root remains the project intake/provenance/integration control surface.

The Forensic Librarian aids Root by:
- reducing ambiguous evidence into actionable packets;
- locating ownership;
- isolating failure nodes;
- recovering provenance;
- identifying exact HOLD dependencies;
- preventing unresolved evidence from becoming generic queue debt;
- returning post-resolution forensic verification.

The Forensic Librarian does not report to Root.

Root does not become the Forensic Librarian's execution owner merely because packets pass through Root intake.

---

## 8. RELATIONSHIP TO MASTER LIBRARIAN

The Forensic Librarian reports to Master Librarian.

Master receives:
- forensic state readback;
- unresolved cross-T conflicts;
- unresolved ownership contradictions;
- evidence that a T-routed corrective action failed;
- evidence that Root intake did not route or preserve a forensic packet correctly;
- final verification that a corrective path resolved the original failure.

The reporting line is therefore:

> **FORENSIC LIBRARIAN → MASTER LIBRARIAN**

while the operational aid line is:

> **FORENSIC LIBRARIAN ↔ ROOT LIBRARIAN**

and the corrective routing line is:

> **FORENSIC LIBRARIAN → ROOT INTAKE → RESPECTIVE T LIBRARIAN**

These lines must not be conflated.

## 10. OUTPUT TERMINOLOGY CORRECTION

Preferred output term:

> **FORENSIC RESOLUTION PACKET**

or, where implementation-ready:

> **CORRECTIVE SOLUTION PACKET**

Avoid treating ordinary narrative reports as the terminal output.

A forensic report may exist as evidence, but the role's completion condition is the creation and routing of the actionable packet required to resolve the evidenced failure.

---

## 11. ACCEPTANCE TEST

This topology is functioning only if a real failure can demonstrate:

1. Forensic Librarian identifies the failure from evidence.
2. Failure is reduced to an exact node/dependency.
3. A corrective packet is created.
4. Correct T Librarian destination is named.
5. Packet enters Root intake at P0/front-of-queue.
6. T Librarian resolves or routes to existing owner.
7. Execution/implementation evidence returns.
8. Forensic Librarian verifies whether the original failure is actually resolved.
9. Master receives final forensic readback.
10. No duplicate T office, Root office, worker, queue, or control plane is created.
