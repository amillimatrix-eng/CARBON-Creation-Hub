## CURRENT OWNER INTENT

Do not manufacture upgrades, patches, addenda, Blue States, governance changes, product changes, or integration proposals merely because an intake path exists.

If there is no evidenced problem, missing invariant, material integration opportunity, or material acceleration opportunity, submit nothing.

If a real improvement is found, write it to Intake with enough evidence and reasoning for ROOT / Governance to decide whether it should be adopted.

## REQUIRED CLASSIFICATION

Every substantive proposed upgrade must be explicitly classified before promotion into durable authority.

Governance should determine whether the proposal is primarily:

1. **PRODUCT UPGRADE**
   - changes a product/utility capability, behavior, UX, acceptance contract, implementation, or versioned product semantics.

2. **BLUE STATE / OPERATING RULE**
   - changes reusable Matrix operating behavior, shorthand, cross-runtime practice, execution discipline, or non-governance operational continuity.

3. **GOVERNANCE UPGRADE**
   - changes authority, classification, evidence standards, intake treatment, promotion rules, lifecycle state, adjudication, or control logic.

4. **ECOSYSTEM / INTEGRATION UPGRADE**
   - changes interoperability, adapters, cross-product invocation, external-provider integration, data contracts, ecosystem routing, or shared capability boundaries.

5. **NO-ACTION / REJECT / ALREADY-SUBSUMED**
   - no material value, duplicates existing authority, conflicts with controlling state, lacks evidence, or would add complexity without sufficient benefit.

Mixed proposals must identify a primary classification and any secondary affected surfaces. Classification must not silently promote authority across layers.

## PROMOTION RULE

**CLASSIFY FIRST → IDENTIFY AUTHORITY TARGET → CHECK CONFLICTS / DUPLICATION → ASSESS VALUE → PROMOTE ONLY TO THE CORRECT LAYER.**

A proposal being useful does not automatically make it:
- product canon;
- Blue State;
- governance law;
- Matrix-wide behavior;
- integration authority.

Promotion must match the scope actually evidenced.

## VALUE TEST

Before promotion, Governance should assess whether the proposal materially improves one or more of:

- product quality;
- Matrix reliability / continuity / truthfulness;
- utility effectiveness;
- integration with other AMX or external ecosystems;
- speed to commercial / operational goals;
- reduction of drift, duplication, ambiguity, false dependency, or Owner intervention;
- evidence quality / verifiability;
- maintainability / reversibility / compatibility.

A proposal that adds complexity without material gain should not be promoted.

## CONFLICT TEST

Governance must identify whether the proposed change:

- conflicts with current product authority;
- conflicts with an active frozen build target;
- duplicates an existing rule or capability;
- changes authority boundaries;
- introduces a second implementation of an existing shared capability;
- creates a new dependency where one is not required;
- weakens an existing acceptance standard;
- silently changes historical provenance or current-state interpretation.

Where conflict exists, modify, defer, supersede explicitly, or reject. Do not silently stack contradictory authority.

## NO-SYNTHETIC-UPGRADE INVARIANT

**NO EVIDENCED PROBLEM OR MATERIAL OPPORTUNITY → NO PATCH.**

**INTAKE CAPACITY != REQUIREMENT TO PRODUCE INTAKE.**

**ACTIVITY != IMPROVEMENT.**

**MORE RULES != BETTER GOVERNANCE.**

This is intended to prevent proposal inflation, governance noise, speculative architecture, and self-generated work that does not move AMX toward its actual goals.
