## 4. PRIORITY CORRECTION MEASURES

### P0-A — Repair READY generation in the existing runner

Modify the existing overdrive runner; do not create another worker or queue.

Required behavior:
- external_action_ready must be derived every regeneration, not preserved as manual metadata only;
- ready_count used for commercial execution must represent externally executable work, not every due review/monitor item;
- executable_order must prioritize/filter externally consequential executable items;
- review/monitor/due-thread checks must remain visible but must use a distinct non-execution state such as REVIEW_DUE / WAITING_REVIEW rather than READY;
- blocked/repair/human/provider-gated items must never silently return to execution READY;
- regeneration must preserve explicit HOLD_CAPABILITY_GAP / WAITING / BLOCKED semantics from authoritative opportunity state.

Acceptance:
- regenerate claims twice from the same authoritative ledger;
- readback must remain stable;
- manually corrected non-executable items must not reappear as external READY;
- external_ready_count, ready_count and executable_order must be internally consistent.

### P0-B — Enforce furthest-state recovery before discovery

Before any broad search/discovery pass, the worker must recover:
- substantive inbound buyer replies;
- OFFER_PRESENTED / NEGOTIATING / explicit next-step threads;
- current package/offer state;
- due follow-ups;
- accepted scope/price if any;
- receivable/payment state;
- exact next commercial action.

A live buyer response such as Face Production must outrank cold discovery unless blocked or materially inferior by evidence.

Acceptance:
- next scheduler-origin run explicitly identifies the furthest live buyer states first;
- no material buyer response can disappear from active commercial priority merely because claims/signals regenerate.

### P0-C — Make state retention durable and single-source

Do not rely on prompt memory or manually patched derivative files.

Required:

- claims/signals are derived routing views only;
- a material external action or buyer response updates the authoritative opportunity state first or atomically with derivative routing state;
- derivative regeneration must never downgrade later lifecycle state to earlier generic READY/WAITING semantics;
- preserve exact next action, due time, thread/message IDs, offer/package version, and payment state.
