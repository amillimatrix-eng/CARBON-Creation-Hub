## 3. FORX TWO-BRANCH ARCHITECTURE

### FORX-W — WORKING / FORENSIC BRANCH

Purpose:

- investigate failures;
- recover provenance;
- isolate failure nodes;
- use FORX-owned inspectors/managers/mechanisms;
- build specific corrective solutions;
- produce actionable forensic packets;
- route every formal packet through Intake;
- assign the correct primary T Librarian destination;
- mirror every packet to FORX-V for completion tracking.

FORX-W does not close work merely by reporting a problem.

Its terminal output is an actionable packet.

---

### FORX-V — VERIFICATION / CONSOLIDATION BRANCH

**Placement:** between ROOT and MASTER.

Purpose:

- receive a mirror of every FORX-W packet;
- track its routed destination;
- receive downstream completion/implementation evidence;
- verify whether the requested correction was actually performed;
- test whether the original failure node is resolved;
- detect false closure / configuration-only closure;
- consolidate cross-T results;
- identify unresolved dependencies or failed routing;
- return verified final readback to MASTER;
- aid ROOT by exposing incomplete or contradictory resolution states.

FORX-V is not a second Intake and not another Governance branch.

It is the completion-assurance / consolidation branch of FORX.

## 9. CLOSED-LOOP RULE

A FORX packet is not complete because:
- it was indexed;
- a T Librarian acknowledged it;
- code/config changed;
- a manager said fixed;
- a receipt exists.

Closure requires:

1. packet created;
2. routed to correct T Librarian;
3. corrective action executed by correct owner;
4. evidence returned;
5. FORX-V checks the evidence;
6. original failure node re-tested;
7. result classified RESOLVED / PARTIAL / FAILED / REGRESSED / HOLD;
8. MASTER receives the consolidated readback.

If FAILED / REGRESSED / PARTIAL:
**FORX-V → FORX-W** and a new bounded corrective packet is created.
