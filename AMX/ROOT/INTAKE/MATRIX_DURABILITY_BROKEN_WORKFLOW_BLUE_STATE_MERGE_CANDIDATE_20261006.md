## 2. DEFINITIVE CORE DEFINITIONS

### 2.1 DURABLE MATRIX

A **DURABLE MATRIX** is an operating Matrix whose authorized state can be reconstructed, resumed, and advanced from durable evidence without depending on transcript memory, model recollection, hidden context, or Owner re-explanation.

A Matrix is durable only when every active mandate-bearing workflow preserves, at minimum:

| Required durable element | Definition |
|---|---|
| Mandate | What the worker/lane is authorized and required to accomplish. |
| Execution owner | The one current authorized worker/lane responsible for execution, respecting single-writer controls where applicable. |
| Furthest evidenced state | The strongest proven lifecycle/operational state already achieved; later workers resume from here rather than restart. |
| Exact next action | The smallest lawful action required to advance the workflow. |
| Dependencies | Every material provider, credential, human, authority, tool, transport, rights, payment, data, resource, or external-party gate. |
| Dependency state | ACTIVE / SATISFIED / SUPERSEDED / NO_LONGER_REQUIRED. |
| Authority boundary | What the worker may and may not do, including spend, external-account, legal, security, KYC, rights, and role limits. |
| Routing/fallback | The normal route plus lawful alternate route(s) if a local dependency fails. |
| Evidence/receipts | Durable proof sufficient to support the claimed state. |
| Continuity/succession | How state survives continuation, restart, worker replacement, scheduler failure, or owner handoff. |
| Closure standard | Exact evidence required before the workflow can be called closed. |
| Capability/context state | Any learned or assembled state that materially changes worker capability and must survive continuation; this includes the RGR-03 30-image state if governance verifies its semantics and applicability. |

**Durable means reconstructable + executable + evidence-bound.**

A file existing somewhere is not sufficient. A durable state must be usable by the owning execution chain without reconstructing meaning from transcript history.

---

### 2.2 BROKEN WORKFLOW

A **BROKEN WORKFLOW** is any active workflow in which the authorized objective cannot reliably progress from the furthest evidenced state to the next lawful state because execution, state, dependency handling, ownership, routing, persistence, or acceptance is defective.

A workflow is definitively BROKEN when **any one** of the following is true:

| Broken condition | Exact meaning |
|---|---|
| Ownerless executable work | ACTIVE mandate + nonterminal executable obligations + no evidenced live execution owner. |
| State loss | Material prior state exists but is not recovered by the current worker. |
| State regression | Regeneration/restart downgrades or overwrites a later valid state. |
| False readiness | Work is labeled READY even though it is review-only, blocked, human-gated, provider-gated, authority-gated, or otherwise non-executable. |
| Lost next action | The current system cannot state the exact next lawful action for a material open item. |
| Unscoped dependency | One local blocker is allowed to idle unrelated executable work. |
| No fallback | A failed route stops the workflow although another already-authorized lawful route exists. |
| Continuity failure | Restart, handoff, scheduler wake, worker replacement, or context loss requires manual reconstruction of material state. |
| Runtime/durable desync | Durable configuration says one thing while live execution behaves differently, and no authoritative reconciliation resolves the conflict. |
| Configuration-only recovery | Prompt/config/state-file changes exist but no attributable runtime/behavioral acceptance proves the repair. |
| Evidence failure | The system claims progression or closure without evidence sufficient for that exact state. |
| Terminal-state misclassification | Intermediate progress is presented as terminal success. |
| Capability-state loss | Previously evidenced learned capability is no longer behaviorally available and is not durably recoverable. |
| Duplicate-owner conflict | More than one writer can independently mutate the same governed workflow without an authorized multi-writer design. |
| Zero-writer dead state | Single-writer protection leaves no current executor while executable work remains. |

A broken workflow may still emit logs, receipts, searches, drafts, ticks, or partial actions. Activity does not make it healthy.

---

### 2.3 BROKEN MATRIX

A **BROKEN MATRIX** is a Matrix in which at least one **required active mandate** has a BROKEN WORKFLOW and the break is not contained by an evidenced, authorized recovery/succession mechanism that preserves the terminal objective.

Therefore:

**ACTIVE MANDATE + NONTERMINAL EXECUTABLE OBLIGATIONS + BROKEN WORKFLOW + NO RELIABLE CONTAINMENT/RECOVERY = BROKEN MATRIX.**

This does not mean every lane is dead.

A Matrix may be:

| Matrix health state | Definitive test |
|---|---|
| HEALTHY | Every active mandate has a live owner, durable state, exact next action or valid scoped wait/block, evidenced continuity, and no unresolved contradiction that prevents reliable progression. |
| DEGRADED | One or more routes/capabilities are impaired, but every affected mandate still has at least one evidenced lawful continuation path and state integrity is preserved. |
| BROKEN | At least one required active mandate cannot reliably continue or retain state, and recovery is not yet behaviorally proven. |
| UNKNOWN | Evidence is insufficient to classify health. UNKNOWN must not be converted to HEALTHY or FAILED by assumption. |

A BROKEN Matrix may still have functioning sub-systems. The classification concerns objective continuity, not whether every component is offline.

## 3. WORKFLOW STATE DEFINITIONS

These are operational states. They do **not** replace the project lifecycle states PRESENT → INDEXED → ACCEPTED → MERGED → CONSOLIDATED → CANON/FROZEN.

| Operational state | Definition |
|---|---|
| ACTIVE | Mandate is live and not terminal. |
| DISCOVERED | A possible opportunity/work item exists but is not yet proven executable or valuable. |
| QUALIFIED | Evidence supports relevance/fit and the item is worth advancing within mandate. |
| REVIEW_DUE | A review/check is due, but no external/actionable execution is yet proven. |
| READY | Internal prerequisites are satisfied and a lawful next execution action exists. |
| EXTERNAL_READY | A lawful externally consequential action can be taken now through an available authorized route. |
| EXECUTING | An authorized action is currently underway. |
| WAITING | Progress correctly depends on an external event/time condition; unrelated work must continue. |
| BLOCKED | No lawful action exists on the affected scope because a material dependency prevents progress. The exact blocker and return condition must be recorded. |
| HOLD | Governance/authority/capability review prevents execution until an explicit condition is satisfied. HOLD is not terminal. |
| COMPLETED | The bounded work item completed; receipt/evidence exists. This does not imply the broader mandate is terminal. |
| CLOSED_VERIFIED | The exact closure standard is proven with durable evidence. |
| FAILED | The bounded action/work item definitively failed; failure evidence exists. Failure does not automatically close the mandate if another route remains. |
| DEGRADED | Execution remains possible but with reduced capability, route availability, or quality. |
| UNKNOWN | Current state cannot be determined from evidence. |
| SOURCE_REMEDIATED | Code/config/durable source has been corrected; runtime acceptance not yet proven. |
| RUNTIME_VERIFIED | Corrected behavior has executed in the target runtime and matches the intended logic. |
| BEHAVIORALLY_ACCEPTED | Repeated attributable execution demonstrates the repaired capability under real work and preserves state across continuation. |

### Commercial terminal truth

For revenue-directed work, the existing Owner law remains controlling:

**PAID is terminal success.**

DISCOVERED, QUALIFIED, OFFERED, SUBMITTED, RESPONDED, NEGOTIATING, CONTRACTED/AWARDED, INVOICED/RECEIVABLE, or similar states are progression only unless the Owner defines another terminal condition.

No new commercial state machine is created by this candidate.

## 4. DEPENDENCY DEFINITIONS

Dependencies are scoped blockers or prerequisites. They are not permission to idle unrelated work.

| Dependency type | Definition |
|---|---|
| AUTHORITY | Required governance/owner/role authority is not currently evidenced. |
| CREDENTIAL | Required authenticated credential/token/account access is unavailable or unverified. |
| HUMAN_AUTHENTICATION | Provider requires a human-only login, MFA, CAPTCHA, identity step, or equivalent action that cannot lawfully be automated. |
| PROVIDER | External provider/service is unavailable, degraded, rejected, rate-limited, or imposes a route-specific restriction. |
| TRANSPORT | Required delivery/action channel is unavailable, e.g. browser, email write path, API route. |
| CAPABILITY | Existing worker/tool cannot perform the required task to the needed standard. |
| CONTEXT_STATE | Required learned/assembled working state is absent or not durably recoverable. |
| DATA_EVIDENCE | Required facts/evidence are missing or insufficient to support the next state. |
| RIGHTS_LEGAL | Rights, licensing, consent, legal, jurisdictional, or policy condition prevents action. |
| PAYMENT | Payment rail, receivable, settlement evidence, payout onboarding, or bank/provider verification is missing. |
| RESOURCE | Budget, metered credits, compute, quota, capacity, or provider limits constrain the route. |
| EXTERNAL_COUNTERPARTY | Progress correctly depends on a buyer, prospect, platform, reviewer, or other external actor. |
| SCHEDULER_RUNTIME | Worker/watcher/scheduler is disabled, failing, stale, non-waking, or unable to persist state. |
| OWNERSHIP | Correct execution owner is missing, conflicting, or not evidenced. |

### Dependency states

Only these durable dependency states should be used unless Governance explicitly extends them:

| Dependency state | Definition |
|---|---|
| ACTIVE | Still materially limits the affected work. |
| SATISFIED | Condition is proven resolved. |
| SUPERSEDED | A later valid route/state makes the prior dependency no longer controlling while provenance remains. |
| NO_LONGER_REQUIRED | The affected work changed such that the dependency is no longer needed. |

If the dependency's condition cannot be determined, the evidence state is **UNKNOWN**; do not invent a fifth dependency lifecycle state.

## 5. RESOLUTION / REMEDIATION DEFINITIONS

| Resolution state | Definition |
|---|---|
| DETECTED | Failure/contradiction has been identified. No repair implied. |
| CONTAINED | Damage/duplication/state loss has been bounded; progression may still be impaired. |
| SOURCE_REMEDIATED | Source/config/durable state was corrected. Runtime behavior remains unproven. |
| RUNTIME_VERIFIED | Corrected runtime executed and produced the expected local behavior. |
| BEHAVIORALLY_ACCEPTED | Real work across repeated attributable runs proves restored capability, state retention, and correct routing. |
| CLOSED_VERIFIED | Governing closure standard is satisfied with durable evidence. |

**DETECTED ≠ REPAIRED.**  
**SOURCE_REMEDIATED ≠ RUNTIME_VERIFIED.**  
**RUNTIME_VERIFIED ≠ BEHAVIORALLY_ACCEPTED.**  
**BEHAVIORALLY_ACCEPTED ≠ CANON.**

Lifecycle authority remains separate.
