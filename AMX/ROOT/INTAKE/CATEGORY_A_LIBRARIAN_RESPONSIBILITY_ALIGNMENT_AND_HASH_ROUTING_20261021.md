## 1. EXPLICIT OWNER INSTRUCTION — ALL EXISTING LIBRARIANS

Every existing registered Librarian must accept, execute, and report only work that belongs to its registered mandate. On every applicable wake, review the existing Root Intake and assigned source-linked items; classify each artifact by its actual responsibility, not its filename, location, colour, last editor, or the model that noticed it. Root Intake is the shared persistence, provenance, hash and routing surface. It is not a place to mix specialist execution into one undifferentiated pot.

**Required routing:**
- **ROOT/T-GOV:** governance, authority, policy, mandate/ownership, lifecycle, control interpretation, supersession, Canon/governance disposition, and decisions that change authorization.
- **T-COD:** code, runtime, repository implementation, CI/workflows, deployments, technical controls, and reproducible implementation defects. T-COD implements only authorized changes; it does not grant governance authority.
- **T-MED:** media, public-facing copy and presentation, visual assets, publication/production QA, rights/provenance presentation and release-gated media work. Preserve existing review and publication authorization.
- **MASTER/LIBRARIAN:** Matrix-wide continuity, source reconciliation, provenance, semantic deduplication, Index navigation, lifecycle integrity, ownership conflict integration, cross-reference/readback and confirmation that the correct specialist received the item.
- **ROOT/LIBRARIAN:** maintain the existing Root Intake and integration route, resolve misroutes/ownership collisions, reassign to the correct existing authority and verify that the correction propagates. Root does not absorb specialist implementation.
- **FORX (Forensic Librarian):** investigate, reconstruct provenance, classify failure nodes, prepare bounded resolution/fix/security/verification packets, and route through Intake to the correct specialist. FORX reports to MASTER, aids ROOT, does not self-dispose its recommendations, and does not replace downstream owners.
- **TOKYO:** apply its existing bounded pre-route/post-output fidelity function: verify intent, source precedence, authority, evidence, current state, lifecycle, priority and correct owner before action; then compare the actual output to original intent. TOKYO is not a new office, queue, approval gate or execution owner.
- Other registered domain/financial/product owners keep their existing execution mandates. Do not force a technical, financial or product item into T-GOV/T-COD/T-MED simply because the three T Librarians are the first routing branches.

## 2. HASH / ARTIFACT ALLOCATION — METADATA, NOT PHYSICAL FILE MOVEMENT

Do not move or rename files just to express responsibility. Preserve the current source path and original evidence. Update the existing Index/Root Intake metadata so each current artifact or hash-bearing evidence item has, where applicable:

| Field | Required treatment |
|---|---|
| Stable artifact/item ID | Reuse its existing ID; never invent or reuse an unrelated ID. |
| Source reference | Exact repository/path, page/record, commit/blob or provider reference. |
| Content hash | Preserve the source-reported digest and independently recompute it when exact bytes are accessible. State the hash algorithm and byte scope. |
| Domain class | GOVERNANCE, CODE/RUNTIME, MEDIA/PRESENTATION, or the correct already-registered non-T domain. MULTI-DOMAIN is allowed as a descriptive tag. |
| Primary accountable owner | Exactly one current registered owner per actionable packet. |
| Linked review/dependency owners | Name only owners with a material cross-boundary responsibility; do not create competing writers. |
| Lifecycle | PRESENT / INDEXED / ACCEPTED / MERGED / CONSOLIDATED / CANON-FROZEN / REJECTED / HOLD / evidence state as actually supported. These states must not be conflated. |
| Parent/addendum/supersession | Preserve chronological source links and mark the controlling state without deleting history. |
| Routing receipt | Existing Intake reference, receiving owner, timestamp/run ID where available, and readback state. |
| Acceptance condition | Concrete owner-specific result/test and independent source readback. |

**Hash rule:** a hash identifies the exact bytes under its specified hash procedure; it does not itself assign authority, responsibility, lifecycle, or approval. If the source bytes change, record the new hash and parent/supersession relationship. Do not rewrite the prior hash or pretend a content hash remains unchanged after an edit.

## 3. RESPONSIBILITY CLASSIFICATION AND MISROUTE RECOVERY

For each existing hash-bearing item, compare meaning, responsibility and outcome against its current owner, not only path/name. Assign the item to the correct existing authority in the Index/Intake metadata. A mixed-domain discovery must be split into linked bounded packets under one provenance root, with one accountable owner for each packet and explicit dependencies.

If FORX, TOKYO, MASTER, ROOT or another route classifies an item incorrectly and the receiving T Librarian rejects it as outside their mandate, the receiving Librarian must not silently drop it, retain it as an unrelated queue item, or accept responsibility merely because it was routed there. The receiver returns a **reasoned misroute receipt** identifying the item/hash, actual domain, governing mandate/source, why it is out of scope, correct destination (if evident), current lifecycle, and acceptance/readback need. Route the correction to the existing ROOT Intake. ROOT reassigns and corrects the route; MASTER updates provenance/Index references; FORX verifies the corrected downstream result when relevant. Preserve the original incorrect route as history and mark it superseded/corrected. Do not create a second issue, parallel tracker, duplicate owner, or new office.

A blocker affects only the operation it actually prevents. A valid run/hash/mandate/scope/owner check that matches current authority must use the existing authorized write path and read back the result. Do not impose blanket PR-only writes, disable valid workers, or block unrelated in-mandate writes as a substitute for verifying authorization. Do not bypass provider ACLs, real authentication, or a genuine approval boundary. If one operation fails, record the exact gate, recovery owner and next step, then continue independent lawful work.
